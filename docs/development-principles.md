# 项目开发原则

本文件定义本项目不可动摇的核心开发原则。所有 AI Agent 在进行技术规划、代码实现和
代码审查时都必须遵循。若具体设计与这些原则冲突，应先明确冲突并修正设计，不得在代码中
保留两套语义。

## 第一条：策略迭代优先（Strategy Iteration First）

**核心：** 项目的首要目标是降低新策略从开发、回测到比较验证的成本，支持快速迭代
新策略。

- **1.1（低摩擦扩展）：** 新增策略只应实现策略逻辑、声明依赖并完成注册，不应修改
  Runner、回测引擎或基础设施。
- **1.2（稳定边界）：** 策略只依赖稳定、只读且绑定决策时点的公开契约，不得直接读取
  Raw、Canonical 文件或基础设施实现。
- **1.3（关注点分离）：** 因子研究、策略信号、订单执行、回测和绩效分析必须保持独立，
  不得为了短期开发速度混合职责。
- **1.4（直接演进）：** 项目尚未发布。设计变化应直接落实为最终结构，不创建旧接口、
  旧字段或旧产物的兼容层。

## 第二条：简单性原则（Simplicity First）

**核心：** 使用能够清晰完成当前需求的最简单方案，不为假想的未来需求增加复杂度。

- **2.1（YAGNI）：** 只实现当前任务和权威设计文档明确要求的能力，不预建扩展点、
  通用框架或备用流程。
- **2.2（既有能力优先）：** 优先使用 Python 3.12 标准库和项目已经采用的依赖。新增
  依赖必须解决明确问题，并说明标准库及既有依赖为何不足。
- **2.3（反过度工程）：** 优先使用直接的数据结构、冻结 `dataclass`、严格 Pydantic
  模型和职责清晰的类；没有明确收益时，不引入多层继承、元类、动态注册或复杂设计模式。
- **2.4（最小变更）：** 每次变更只覆盖任务所需范围，同时完成必要的代码、测试和文档
  同步，不顺带重构无关模块。

## 第三条：明确性原则（Clarity and Explicitness）

**核心：** 代码首先要让维护者准确理解，其次才是让机器执行；依赖、状态、类型和失败
路径都必须显式可见。

- **3.1（显式错误处理）：** 不得使用裸 `except`，不得静默吞掉异常，也不得用空处理
  掩盖失败。受控错误应转换为明确的领域或应用错误，未知异常只在进程边界统一处理。
- **3.2（无可变全局状态）：** 模块级常量可以存在，但运行时状态不得通过全局变量、
  单例或导入副作用传递。依赖应通过构造参数或方法参数显式注入。
- **3.3（类型即契约）：** 公开 API 必须具有完整、严格的类型标注，不使用兼容性的
  `*args`、`**kwargs`，不依赖隐式类型转换或动态属性约定。
- **3.4（文档说明意图）：** 公开模块、类、方法和函数必须使用中文 docstring，说明职责、
  入参、返回值和关键异常。行内注释解释“为什么”，不重复代码已经表达的“是什么”。
- **3.5（显式资源生命周期）：** 网络连接、数据库会话、文件、Worker 和线程必须在清晰的
  作用域中创建和关闭，不得在模块导入期间启动外部副作用。

## 第四条：单一职责原则（Single Responsibility）

**核心：** 每个包、模块、类和方法只承担一个清晰职责，并遵守既定依赖方向。

- **4.1（高内聚、低耦合）：** 行为应归入职责明确的能力包。接口层只做输入输出适配，
  Application 只编排用例，业务能力不依赖 UI、组合根或基础设施具体实现。
- **4.2（消费者侧 Protocol）：** 需要跨边界注入时，由消费者定义小而明确的 `Protocol`；
  不创建覆盖多个用例的“上帝接口”，也不让基础设施反向定义业务契约。
- **4.3（方法归属明确）：** 不新增模块级孤立函数。逻辑应根据状态依赖归入实例方法、
  类方法或静态方法；只有稳定公开 API 或框架入口可以保留模块级函数。
- **4.4（唯一组合根）：** `bootstrap` 是具体依赖的唯一组合根。CLI、Dashboard、
  Application 和业务能力包不得自行装配基础设施实现。

## 第五条：快速反馈原则（Fast Feedback）

**核心：** 快速迭代来自短而可信的反馈循环，不能以跳过边界检查和测试为代价。

- **5.1（先测最小闭环）：** 优先编写和运行与变更直接相关的单元测试；跨层行为再使用
  集成测试，避免所有验证都依赖完整系统启动。
- **5.2（依赖可替换）：** 时间、UUID、环境身份、供应商响应和外部端口必须可注入，
  单元测试使用 fake 或 stub，不访问真实网络和生产数据。
- **5.3（静态门禁）：** 交付前至少运行 Ruff、严格 mypy 和相关 pytest。修改架构边界、
  数据库迁移、CLI 或 Dashboard 时，必须追加对应专项验证。
- **5.4（失败可诊断）：** 测试和错误信息应指出失败的契约与原因，禁止只验证“未抛异常”
  或用实现对实现比较替代明确的预期结果。
